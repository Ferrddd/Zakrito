# Мультиагентная система рекомендаций для производства ДТ

АВТ → гидроочистка → блендинг. Система получает состояние процесса, оценивает качество и риск выхода за
спецификацию, проверяет ограничения и формирует объяснимую рекомендацию оператору — или честно
отказывается, если надёжной рекомендации нет. Приоритет: **качество и жёсткие ограничения важнее
экономики** (ТЗ п.1).

## Ключевые свойства решения

- **Модульность.** Каждый агент — независимая реализация общего протокола (`src/agents/base.py`).
  Оркестратор не знает, реальный агент перед ним или заглушка: качество, надёжность и оптимизация
  подключаются через конструктор `Orchestrator(quality, reliability=..., optimizer=...)`, а любой из
  них можно заменить (например, `RemoteQualityAgent` — тот же агент качества, но по HTTP) без изменения
  логики цикла принятия решения.
- **Трассировка агентов.** Каждый цикл фиксируется целиком: `Recommendation.trace_id` связывает вход
  (`ProcessState`), оценки всех агентов (`AgentReport`, `ReliabilityAssessment`), проверенные сценарии
  (`CheckedScenario` с деталями каждой жёсткой проверки) и итоговую рекомендацию — всё пишется в
  аудит-лог `data/converted/audit/cycles.jsonl` (JSON Lines, один цикл = одна строка). Отдельно
  `CycleContext.agent_calls` и `Orchestrator.stats` считают, сколько раз и с каким результатом был вызван
  каждый агент за цикл — это видно и в консоли демо-прогона, и в UI. Заглушки явно помечаются
  (`Recommendation.stubbed_agents`), чтобы результат нельзя было спутать с оценкой реального агента.
- **Честный отказ.** Система осознанно возвращает `no_recommendation`/`escalate` при устаревших данных,
  критическом состоянии оборудования или отсутствии допустимого сценария — вместо того чтобы выдать
  сомнительную рекомендацию.

## Архитектура

```
 данные (parquet) ──► ProcessState ──► Оркестратор ──┬─► Агент качества       прогноз серы, риск, отказ
                                          │          ├─► Агент надёжности     severity/risk_class, факторы
                                          │          └─► Агент оптимизации    допустимые сценарии + score
                                          ▼
                       проверка жёстких ограничений на каждом сценарии
                       (what-if через агент качества; сумма долей = 100%)
                                          ▼
              Recommendation (объяснение, альтернативы, trace_id) + аудит-лог cycles.jsonl
```

Оркестратор (`src/orchestrator/orchestrator.py`) — один цикл: качество → надёжность → есть ли риск →
(оптимизатор → отбрасывание сценариев, нарушающих ограничения → выбор лучшего по score среди допустимых)
→ рекомендация. Статусы: `stable` (действий не нужно), `action`, `risk_no_optimizer`,
`no_recommendation` (отказ), `escalate` (критический режим оборудования — решение за оператором).

## Структура

```
src/
  agents/
    base.py                 протокол Agent (общий контракт для всех ролей)
    quality/                агент качества: прогноз серы, риск, отказ при устаревшем ПАК
    reliability/             агент надёжности: severity_index, тренд ΔP, доля аномальных тегов
  orchestrator/
    orchestrator.py         цикл принятия решения, аудит, статистика вызовов агентов
    contracts.py            Scenario, Recommendation, протоколы и заглушки надёжности/оптимизации
    adapters.py             AgentReport ↔ общие схемы (agents_schemas.py)
    clients.py              RemoteQualityAgent (HTTP) — тот же протокол, что и локальный агент
  schemas/
    process_state.py        ProcessState / AgentReport
    agents_schemas.py       схемы команды: Snapshot, QualityAssessment, Reliability*, OptimizationInput
  data_pipeline/            загрузка/фичи/сплиты
ui/                         дашборд: живые циклы оркестратора, статусы, объяснения
scripts/run_orchestrator.py прогон оркестратора по историческому периоду (консоль / UI / файл)
tests/
```

## Запуск

Подробный порядок запуска (Docker и локально) и чек-лист перед отправкой — в [`RUN.md`](./RUN.md).

**Для Windows 11** рекомендуется вариант с Docker Desktop (WSL2-бэкенд) — он не зависит от `make`/bash и
работает одинаково на любой ОС:

```powershell
docker compose up --build
```

Локальный запуск без Docker (`make ...` ниже) на Windows требует WSL2 или Git Bash — подробности и
ограничения в [`RUN.md`](./RUN.md#b-локально-разработка-без-docker).

Коротко, локально (Linux/macOS/WSL2):

```bash
make install && make copy_env
make data_pipeline && make train_quality && make train_reliability
make quality_api                                        # терминал 1: агент качества (:8001/docs)
make ui                                                  # терминал 2: дашборд (:3000)
make orchestrator_ui START=2026-06-01 STEPS=50 EVERY=6   # терминал 3: прогон истории в UI
make test && make lint
```

Одной командой (Docker):

```bash
docker compose up --build
```

## Допущения

| # | Допущение | Где |
|---|---|---|
| 1 | Сера в ppm ≈ мг/кг; лимит 10 из ТЗ п.4 | `quality/config.yaml` |
| 2 | Риск = тревога классификатора **или** p90 > лимита (консервативно) | `orchestrator.has_quality_risk` |
| 3 | ПАК старше 24 ч → отказ от рекомендации | `QualityAgent.max_pak_age_min` |
| 4 | Технологические диапазоны управляющих тегов не заданы в исходных материалах — заданы как явные
    модельные допущения (правило границ ТЗ п.4) | `orchestrator._check`, конфиг оптимизатора |
| 5 | Оркестратор независимо перепроверяет каждый сценарий оптимизатора (what-if по качеству +
    собственные ограничения) — предложение оптимизатора само по себе не гарантирует выбор | `orchestrator._check` |

## Демо-сценарии

Прогон `make orchestrator_ui`/`make orchestrator_demo` по историческому периоду показывает все сценарии
из ТЗ п.6: устойчивый период без лишних действий, период с риском по качеству и предложенным изменением
режима, ситуацию с неполными/устаревшими данными (честный отказ) и полный цикл обмена между агентами —
трассировку каждого шага можно посмотреть в `data/converted/audit/cycles.jsonl` или в UI.
